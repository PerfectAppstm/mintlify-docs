Every real-world project touches more than one database. You need a local database for development, a staging database for testing, and a production database for live traffic — and each one has its own connection details. Environments in 2AM Database++ solve this by letting you define multiple named connections inside a single project, so you can run the same migrations against any target without editing configuration files or juggling credentials manually.

## What Is an Environment?

An environment is a named connection configuration that lives inside your project's `configuration.yml`. Common environment names are `local`, `dev`, `staging`, and `production`, but you can name them anything that fits your workflow. Each environment specifies how to connect to a specific database and which credential strategy to use.

Here is a minimal example of the `environments` section in `configuration.yml`:

```yaml
environments:
  local:
    credentialType: direct
    host: localhost
    port: 5432
    database: myapp_dev
    username: postgres
    password: postgres

  staging:
    credentialType: dotenv
    dotenvFile: .env.staging

  production:
    credentialType: aws
    secretId: myapp/production/db
    region: us-east-1
```

Each top-level key under `environments` is the environment name you reference when running CLI commands or selecting a target in the desktop app.

## Credential Types

2AM Database++ supports three strategies for supplying database credentials. Choose the one that matches your security requirements and deployment setup.

### 1. Direct Credentials

Direct credentials are hardcoded values written inline in `configuration.yml`. They are the simplest option and work well for local development where security is not a concern.

```yaml
credentialType: direct
host: localhost
port: 5432
database: myapp_dev
username: postgres
password: postgres
```

**Do not use direct credentials in staging or production environments.** Hardcoded passwords in configuration files are a security risk, especially when the file is committed to version control.

### 2. Dotenv Credentials

Dotenv credentials read connection details from a `.env` file on disk. This keeps secrets out of `configuration.yml` while still being straightforward to manage on developer machines and CI servers.

```yaml
credentialType: dotenv
dotenvFile: .env.staging
```

The specified `.env` file must define the expected variables (host, port, database name, username, and password). The `.gitignore` generated by `2am-smt init` excludes `.env` files from version control by default.

### 3. AWS Credentials

AWS credentials retrieve connection details from [AWS Secrets Manager](https://aws.amazon.com/secrets-manager/) at runtime. This is the recommended approach for production environments because secrets are never stored on disk and access is governed by IAM policies.

```yaml
credentialType: aws
secretId: myapp/production/db
region: us-east-1
```

The tool uses the AWS SDK's default credential chain, so it respects environment variables, shared credential files, and instance/task roles automatically.

## SSL Support

All three credential types support SSL configuration. You can enable SSL and specify certificate paths in the environment block to encrypt connections to your database server. This is strongly recommended for any environment outside of local development.
